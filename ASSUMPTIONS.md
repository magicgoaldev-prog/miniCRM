# Решения и допущения

В ТЗ часть моментов оставлена на усмотрение. Ниже — что зафиксировал сам и что сознательно не делал.

## Где ТЗ допускало разное толкование

Все постановщики в системе равны: любой из них видит все объекты и задачи, может править и принимать работу. Отдельного «владельца» задачи нет.

Исполнитель видит только свои задачи — и в интерфейсе, и при прямом обращении к API. В карточке объекта ему тоже показываются только его задачи, а не весь список по площадке. Объект в списке появляется, пока на нём есть хотя бы одна задача, назначенная на этого исполнителя.

При создании задачи исполнитель обязателен. Переназначить человека можно только пока статус «новая» или «на доработке». В остальных статусах смена исполнителя запрещена.

«Принята» — конечный статус, обратно из него задача не выходит. Постановщик при этом может править текст задачи и удалять её.

Исполнитель сам строки задач в базе не обновляет: смена статуса идёт только через отдельное действие перехода. Удалить объект нельзя, пока на нём остаются задачи — сначала задачи, потом объект. Если задачу удалили, её история статусов уходит вместе с ней.

## Безопасность (как договорили по смыслу ТЗ)

Историю статусов клиент не пишет и не правит — только читает. Статус в таблице задач напрямую не патчится, только через проверенный переход. Открытая регистрация в проекте выключена. Во фронте и в репозитории лежит только публичный ключ; service_role туда не попадает.

Язык интерфейса по умолчанию русский, есть переключение на английский. Это не из ТЗ — добавил для удобства сдачи и демо.

## Что не успел / сознательно не брал

Вложения к задачам, уведомления, realtime-обновления экрана, мягкое удаление записей. На объём 2–3 часов и оценку логики с безопасностью это не влияло.
